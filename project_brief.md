# Project Brief: Контейнеризація ML-моделі класифікації зображень

## 1. Мета проєкту

Підготувати відтворюваний спосіб запуску inference для pretrained-моделі класифікації зображень у Docker. 
Команда має надати два образи:  
- базовий `ml-infer-fat:1.0`
- оптимізований `ml-infer-slim:1.0`  

Обидва образи повинні виконувати однакову задачу на однаковому вхідному зображенні та 
повертати узгоджений результат top-3 predictions.

## 2. Бізнесовий контекст

Контейнеризація спрощує передачу ML-рішення між розробниками, CI/CD та staging.  
Стандартизований Docker image зменшує залежність від локального оточення та 
дає змогу повторювати перевірки в контрольованих умовах.  
AI PM має прийняти delivery-артефакти лише на основі перевірюваних доказів.

## 3. Технічний контекст

Очікувані складові проєкту: 
- `model/model.pt` - файл ваг моделі; 
- `app/inference.py` - код inference;  
- `requirements.txt` - Python-залежності;  
- `Dockerfile.fat` - Dockerfile базового образу;  
- `Dockerfile.slim` - Dockerfile оптимізованого образу;  
- `.dockerignore` - правила виключення зайвих файлів із build context;  
- `README.md` - інструкції збірки, запуску й тестування;  
- `report.md` - звіт із порівнянням образів.

Фактичну наявність і вміст цих файлів команда має підтвердити в репозиторії.

## 4. Призначення inference

Inference виконує передбачення для нового зображення за допомогою вже навченої моделі.  

У межах завдання модель не перенавчається:  
команда забезпечує її запуск у контейнері та повернення top-3 predictions у погодженому форматі. 

До тестування потрібно задокументувати формати:
- input,  
- preprocessing,  
- output,  
- спосіб передачі тестового зображення.

## 5. Delivery-артефакти

Docker image є delivery-артифактом. Він пакує застосунок, runtime та потрібні залежності.  
Його можна збирати, тегувати, перевіряти й передавати між етапами delivery pipeline.  
Приймання охоплює збірку, запуск, inference, розмір, склад файлів і безпеку.

## 6. Необхідність двох образів

1. **Fat:**  
   `ml-infer-fat:1.0` будується на базі `python:3.13`  
   простий варіант для першої перевірки та порівняння.
2. **Slim:**  
   `ml-infer-slim:1.0` будується на базі `python:3.13-slim`  
  оптимізований варіант із multi-stage build, що містить лише необхідні runtime-компоненти.

Обидва образи мають використовувати той самий model artifact і еквівалентну логіку inference.  
Оптимізація має зменшити розмір і зайвий вміст, не змінюючи поведінку моделі.

## 7. Середовища перевірки

1. **Локально:**  
   інженер виконує команди з README, збирає й запускає обидва образи.
2. **CI/CD:**  
   збірка та автоматизовані перевірки повторюються в pipeline.
3. **Staging:**  
   після проходження погоджених перевірок образ тестується в інтеграційному середовищі з безпечною конфігурацією.

Локальний запуск сам по собі не підтверджує production-readiness.
Потрібні докази проходження критеріїв приймання, перевірки залежностей,
безпеки та конфігурації.

## 8. Припущення й відкриті питання

- Архітектура pretrained-моделі, її версія та джерело ще не зафіксовані.  
- Фактичні метрики образів має надати команда.  
- Допустиму числову похибку для prediction scores слід погодити до тестування.  
- Compose-стенд оцінюється окремо від одиничного image; реалізацію потрібно підтвердити.  
- Непідтверджені значення позначаються `TBD`.

## 9. Критерій успіху

Будь-який член команди може клонувати репозиторій, виконати задокументовані команди, 
зібрати обидва образи, запустити inference на однаковому input і підтвердити узгоджені top-3 результати.  
Метрики розміру, часу збірки/запуску, security findings та вмісту образів задокументовані, 
а відкриті ризики мають owners і план дій.
