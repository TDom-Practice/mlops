# Модель загроз — ContractPilot AI

## Обсяг, активи та поверхня атаки

ContractPilot AI — B2B SaaS-платформа для юридичних команд компаній. Сервіс працює в регіонах AWS у ЄС та США. Користувачі взаємодіють із ним через захищений вебзастосунок та API. Кожен запит проходить автентифікацію та авторизацію з урахуванням ідентифікатора tenant і ролі користувача. Далі API gateway отримує релевантні фрагменти документів із tenant-scoped RAG в OpenSearch, передає дані моделі оцінювання ризиків, розгорнутій в EKS, а потім звертається до LLM-провайдера з режимом zero retention. LLM формує пояснення з посиланнями на джерела. Результат, ідентифікатори отриманих фрагментів, версії моделі та промпту, а також результати перевірок безпеки записуються до audit stream. Вихідний вміст документів зберігається відповідно до умов договору з клієнтом.

До найцінніших активів належать договори та playbooks клієнтів, що можуть містити конфіденційну інформацію й персональні дані; ізоляція даних між tenant; облікові дані та ключі шифрування; артефакти моделей; шаблони промптів; набори для оцінювання; аудиторські записи; доступність робочого процесу перевірки договорів.

Основні учасники взаємодії із системою: кінцеві користувачі та адміністратори клієнтів, команда підтримки ContractPilot, інженери ML/MLOps і backend, провайдер LLM, хмарні сервіси, а також зовнішні зловмисники. Користувачі клієнтів можуть завантажувати документи й надсилати запитання. Вибір версії моделі, обхід авторизації та доступ до індексів інших tenant їм недоступні. Інженери працюють через IAM roles із розподілом обов’язків: ML Lead може запропонувати модель, MLOps Lead відповідає за її просування та розгортання, Security Lead контролює доступ і проводить аудит.

Межі довіри та засоби їх захисту визначені на кожному етапі обробки запиту. Трафік між браузером і API захищено за допомогою TLS та автентифікації. API gateway є єдиною точкою доступу до сервісів RAG і LLM. OpenSearch працює в приватному контурі та використовує фільтрацію за tenant, ACL-метадані й шифрування через KMS. Доступ до MLflow обмежено SSO/VPN, а артефакти моделей зберігаються у версіонованому S3. Argo CD застосовує до EKS лише зміни з перевірених Git-комітів; прямий доступ до production через `kubectl` не передбачений стандартним процесом. У логах використовуються псевдонімізовані ідентифікатори замість повного тексту договорів. Gateway перевіряє вхідні дані та результати обробки перед надсиланням відповіді користувачеві.

З огляду на роботу з клієнтами в ЄС, обробка персональних даних має відповідати вимогам GDPR. Для ML-компонентів також враховуються застосовні вимоги EU AI Act, зокрема щодо управління ризиками, простежуваності та людського контролю. Відповідність регуляторним вимогам враховується під час оцінювання загроз, визначення заходів контролю та погодження production-релізів.

## Межі довіри та потоки даних

У системі визначено чотири основні межі довіри:

1. **Client boundary:** браузер і пристрої користувачів взаємодіють із платформою через TLS та API gateway. Автентифікація й авторизація визначають tenant, роль і доступні операції.
2. **Application boundary:** API gateway контролює запити до ML та RAG. Tenant ID встановлюється серверною частиною, а ACL перевіряються перед отриманням документів. Користувацький запит і вміст завантаженого документа розглядаються як потенційно недовірені дані.
3. **Model and data boundary:** OpenSearch зберігає індекси документів, MLflow і S3 використовуються для моделей та їхніх артефактів, а EKS виконує inference. Передавання контексту LLM обмежується даними, необхідними для конкретного запиту.
4. **External provider boundary:** LLM-провайдер отримує лише відібраний контекст через регіональний gateway відповідно до погодженої політики zero-retention. Доступність і умови обробки даних провайдера залишаються окремим зовнішнім ризиком.

Для кожної межі визначено контроль доступу, журналювання та відповідальну роль. Особливу увагу приділено переходу від tenant-scoped RAG до LLM: перевірка прав доступу має завершитися до передавання контексту зовнішньому провайдеру.

Для оцінювання ризиків використовується матриця 3×3.  
Impact:  
**1** — до $25K;  
**2** — понад $25K до $150K;  
**3** — понад $150K або суттєвий регуляторний чи договірний ризик.  
Likelihood:  
**1** — низька,  
**2** — середня,  
**3** — висока.  
Score = Impact × Likelihood:  
**P1** = 6–9,  
**P2** = 3–4,  
**P3** = 1–2.  
Фінансові оцінки враховують сервісні компенсації, витрати на реагування на інциденти, можливий вплив на ARR і потенційні юридичні витрати. Це орієнтири для планування, а не прогноз фактичних збитків.

## Контроль ефективності заходів захисту

Наявність mitigation у реєстрі загроз сама по собі не підтверджує зниження ризику. Для кожного P1-ризику необхідно мати перевірюваний evidence, який демонструє ефективність відповідного контролю.

| Контроль | Спосіб перевірки | Evidence |
|---|---|---|
| Tenant isolation | Спроби отримати документи іншого tenant під час release testing | Результати негативних API-тестів і записи deny events |
| Prompt injection protection | Direct та indirect adversarial tests | Red-team report і результати regression tests |
| Hallucination control | Перевірка відповідей на юридично значущих прикладах | Evaluation report із hallucination rate та citation coverage |
| Model Registry security | Перевірка ролей propose/promote та прав доступу до артефактів | IAM policy review і CloudTrail events |
| Model quality | Порівняння candidate і champion на holdout dataset | MLflow evaluation report із Recall та PSI |
| Audit logging | Перевірка повноти trace для вибірки production-запитів | Loki traces, Grafana dashboards та audit records |

Результати перевірок зберігаються разом із release evidence. Якщо контроль не пройшов перевірку, відповідний P1-ризик залишається відкритим, а production-реліз блокується до усунення проблеми або формального перегляду ризику уповноваженою особою.

## Обробка пріоритетів і residual ризик

Ризики рівня P1 блокують реліз, доки впровадження та ефективність відповідних заходів контролю не підтверджені. Для T-006, T-007, T-008, T-009, T-011 і T-015 підтвердження мають бути частиною перевірок безпеки та відповідності вимогам, визначених у [03_Release_Checklist.md](03_Release_Checklist.md). Для T-004, T-011 і T-014 додатково передбачені сценарії реагування в [04_Incident_Runbook.md](04_Incident_Runbook.md).

Для T-012 прийнято залишковий ризик недоступності LLM-провайдера. У разі збою сервіс переходить у резервний режим: якість відповідей може знизитися, але система залишається доступною та не надає критично важливих тверджень без посилань на джерела. Рішення про прийняття залишкового ризику ухвалює CPO після консультації з керівником із відповідності вимогам.

## Review cadence

Security Lead переглядає реєстр загроз щомісяця, а також після кожного інциденту рівня P1 або P2. AI Safety Lead проводить red-team вправи щокварталу. ML Lead перевіряє навчальні дані та метрики за окремими сегментами під час підготовки кожного candidate-релізу.

Перед впровадженням будь-якого нового data processor, LLM-провайдера, інструмента або способу доступу до даних tenant необхідно повторно оцінити модель загроз і за потреби оновити реєстр.
