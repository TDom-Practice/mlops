# PM Decision Report: Customer Churn Prediction

## 1. Бізнес-контекст ML-задачі

### Яку задачу вирішує модель?
Модель прогнозує відтік клієнтів (Customer Churn Prediction):   
`churn = 1` позначає клієнта з відтоком,  
`churn = 0` - клієнта без відтоку.  
Бізнес-мета - завчасно виявляти ризик втрати клієнтів і мати змогу реагувати.

### Яке рішення або прогноз вона має підтримувати?
Модель має прогнозувати ризик відтоку, щоб команда могла визначати клієнтів, яким варто приділити увагу в першу чергу, і планувати проактивний контакт, додаткову підтримку чи утримувальну пропозицію. Прогноз підтримує рішення команди.

### Хто користувач результату моделі?
У типовому сценарії це Customer Success, CRM/Retention або маркетингова команда, а також бізнес-власник показника відтоку.

### Яка помилка моделі є більш небезпечною?
Для утримання клієнтів потенційно небезпечніший `false negative`: модель не виявляє клієнта, який фактично піде, і команда втрачає можливість вчасно відреагувати.  
`False positive` теж має вартість, бо ресурси витрачаються на клієнта, який міг би залишитися.  
Відносну вартість помилок потрібно підтвердити з бізнес-стейкхолдером.

### Яка метрика має бути головною?
Якщо пріоритет - виявляти якомога більше клієнтів, які підуть, головною метрикою-кандидатом є `recall` для `churn = 1`. Його потрібно оцінювати разом із `precision`, `F1`, confusion matrix і `log loss`, щоб контролювати хибні спрацювання.  
Остаточну метрику та поріг приймання потрібно погодити з бізнесом.  
`Accuracy` не має бути єдиним критерієм, оскільки позитивний клас менш поширений.

**Дані кейсу:** 600 синтетичних записів, 450 train / 150 test, stratified split, `random_state=7`; генерація — `random_state=19`. У навчальному тесті 34 приклади `churn = 1` і 116 `churn = 0`.

## 3. Вибір кандидата для staging / production

**Обраний run: `rf-depth8`, Run ID `cafecb04`.** Це найкращий поточний кандидат для додаткової перевірки, але ще не затверджена production-модель.

### Чому саме цей run?
`rf-depth8` має найвищу accuracy (`0.8733`), найнижчий log loss (`0.3602`), найвищий наведений F1 (`0.6984`) і ROC-AUC `0.8953`. Для нього також збережено model artifact та супровідні файли. Водночас самі по собі найкращі accuracy та loss не доводять, що модель найкраще відповідає бізнес-задачі: важливо, скільки клієнтів із реальним ризиком відтоку вона виявляє.

### Яка метрика стала ключовою?
Для сценарію утримання клієнтів ключовою метрикою-кандидатом є **recall для `churn = 1`**, якщо бізнес насамперед хоче не пропускати клієнтів, які підуть. У `rf-depth8` recall дорівнює `0.6471`: модель виявляє приблизно 22 із 34 позитивних прикладів і пропускає близько 12. Тому результат ще потребує покращення або погодження з бізнесом допустимого рівня пропусків. Остаточний вибір метрики залежить від вартості false negative та false positive.

### Чи є baseline для порівняння?
Так. `majority-baseline` (`cafecb00`) має accuracy `0.7733` і loss `0.5353`, але recall і F1 дорівнюють нулю: він не знаходить жодного позитивного прикладу. Отже, його accuracy вводить в оману й не робить baseline корисним для виявлення churn. Порівняно з ним, `rf-depth8` має кращі accuracy та loss і фактично виявляє частину клієнтів із відтоком.

### Наскільки покращення суттєве?
Порівняно з baseline accuracy зросла з `0.7733` до `0.8733` (**+0.1000**, тобто 10 відсоткових пунктів), а loss знизився з `0.5353` до `0.3602` (**−0.1751**). Це помітне покращення на наданому тестовому наборі. Проте тест містить лише 150 записів, із них 34 позитивні, а дані синтетичні; тому цього недостатньо, щоб стверджувати, що таке покращення буде стабільним на реальних клієнтах.

### Чи є trade-off між метриками?
Так. `rf-depth8` має recall `0.6471`, тоді як `logreg-balanced` має вищий recall — `0.7941`, тобто виявляє більшу частку клієнтів із відтоком, але має нижчу accuracy (`0.6933`) і вищий loss (`0.5865`). `rf-depth4` також має трохи вищий recall (`0.7353`) за `rf-depth8`, але нижчі accuracy (`0.8400`) і F1 (`0.6757`). Отже, вибір залежить від балансу між пропущеними клієнтами та кількістю хибних спрацювань і витратами на утримувальні дії. Варто порівняти моделі за confusion matrix та перевірити різні пороги прогнозу.

### Чи є model artifact?
Так. Для `rf-depth8` показано `model.joblib`, а також `requirements.txt`, `feature_schema.json`, `input_example.json` і `metrics.json`. Це полегшує подальше тестування та відтворення моделі. Для `rf-depth4` model artifact у наданих матеріалах відсутній.

### Чи достатньо інформації для відтворення результату?
**Не повністю.** Для `rf-depth8` є параметри, `random_state`, model artifact і супровідні файли, тому цей run найкраще підготовлений до відтворення серед п’яти експериментів. Але для повної відтворюваності також потрібні версія коду, точна версія або хеш даних, preprocessing pipeline та зафіксовані залежності/середовище. Отже, відтворюваність часткова, а не гарантована.

**PM-рішення: `Need more experiments`.** Залишити `rf-depth8` основним кандидатом для наступного раунду перевірок, але не переводити його до production лише на підставі цих результатів. Погодити з бізнесом допустимий рівень пропущеного відтоку, порівняти фіналістів на репрезентативних даних і зафіксувати критерії приймання до staging.

## 4. Перевірка Grafana/Prometheus метрик

За наданими скриншотами Prometheus можна проаналізувати метрики експериментів і порівняти їх із результатами MLflow UI.

- **Чи видно `mlflow_accuracy`?**  
  Так. Метрика відображається на графіку та в таблиці Prometheus.
- **Чи видно `mlflow_loss`?**  
  Так. Метрика відображається на графіку та в таблиці Prometheus.
- **Чи є мітка `run_id`?**  
  Так. Мітка `run_id` дає змогу пов’язати значення метрик із конкретним запуском моделі.
- **Чи збігаються значення з MLflow UI?**  
  Значення на наданих скриншотах узгоджуються з результатами MLflow UI з урахуванням округлення. Наприклад, для `rf-depth8` accuracy становить `0.8733`, а loss — `0.3602`.
- **Чи можна швидко побачити найкращий run?**  
  За метриками accuracy та loss можна швидко визначити `rf-depth8`: він має найвищу accuracy (`0.8733`) і найнижчий loss (`0.3602`) серед п’яти експериментів. Проте цих двох метрик недостатньо, щоб визначити, чи є він найкращим саме для бізнес-задачі прогнозування відтоку клієнтів.
- **Чи достатньо цих метрик для production-рішення?**  
  Ні. Для рішення про production потрібно також врахувати recall, precision, F1, бізнес-вартість помилкових прогнозів, стабільність моделі та результати перевірки на репрезентативних даних. Для експлуатації моделі додатково потрібні метрики доступності, затримки відповіді, частоти помилок, якості вхідних даних і drift.

### Висновок

**Grafana / Prometheus показує:**

Значення `mlflow_accuracy` та `mlflow_loss` для запусків моделі, які можна порівнювати в часі. Мітка `run_id` допомагає визначити, до якого запуску належить конкретне значення метрики. На графіках також видно розрив приблизно о 08:34 UTC, який у наданому прикладі пов’язаний із перезапуском exporter. Сам по собі цей розрив не свідчить про погіршення якості моделі.

**MLflow UI показує:**

Результати окремих експериментів, їхні параметри, метрики та доступні артефакти. Це дає змогу детальніше порівнювати моделі й перевіряти, які налаштування дали відповідний результат.

**Разом ці інструменти допомагають:**

MLflow - відстежувати експерименти та порівнювати результати моделей, а Prometheus - спостерігати за метриками й змінами їхніх значень. Завдяки цьому можна швидко виявити перспективний run для подальшої перевірки та контролювати показники під час експлуатації.

**Але для production-рішення ще бракує:**

Підтвердження якості моделі на реальних репрезентативних даних, узгоджених із бізнесом критеріїв приймання, оцінки вартості помилок, моніторингу recall та інших показників якості після появи фактичних результатів, контролю data drift, latency, error rate і доступності сервісу, а також налаштованих сповіщень та визначених відповідальних за реагування. Окремо необхідно підтвердити відтворюваність експерименту й готовність моделі до розгортання.

Отже, `rf-depth8` є перспективним кандидатом для подальшого тестування, але наявних метрик недостатньо для остаточного рішення про production.

| Не перевірено якість моделі на різних сегментах клієнтів | Середня | Середній | Проаналізувати метрики на важливих сегментах клієнтів, щоб виявити групи, для яких модель працює гірше. |

**Висновок:** найбільш критичними є ризики вибору моделі за нерелевантною метрикою, неповної відтворюваності експериментів, відсутності rollback-плану та моніторингу після розгортання. До переходу в production необхідно визначити критерії приймання, відповідальних осіб і процедури реагування на погіршення якості моделі.

## 7. PM Decision Report

**Рекомендація: Need more experiments.**

**Обґрунтування:**  
Модель `rf-depth8` є найперспективнішим кандидатом серед п’яти експериментів, але наявних доказів недостатньо для переходу до staging. Вибір моделі лише за accuracy не враховує бізнес-мету - виявлення клієнтів, які можуть припинити користуватися послугою.

**Основні докази:**  
`rf-depth8` має найвищу accuracy (`0.8733`), найнижчий loss (`0.3602`) та F1 (`0.6984`). Для нього збережено `model.joblib` і супровідні артефакти, а Run ID (`cafecb04`) та параметри експерименту зафіксовані. Водночас recall становить `0.6471`, тобто модель виявляє приблизно 22 із 34 клієнтів із відтоком у тестовій вибірці та пропускає близько 12. Модель `logreg-balanced` має вищий recall (`0.7941`), тому необхідно додатково порівняти моделі з урахуванням вартості хибних прогнозів.

**Основні ризики:**  
Повна відтворюваність експерименту не підтверджена, оскільки бракує повної інформації про версію коду та даних. Також не визначено остаточні критерії переходу до staging, rollback-процедуру та відповідальних за production-рішення.

**Що потрібно зробити перед production:**  
Провести додаткові експерименти, перевірити якість моделі на репрезентативних даних і погодити з бізнесом цільові значення recall та інших метрик. Зафіксувати версії коду, даних і залежностей, визначити критерії приймання, налаштувати моніторинг і підготувати rollback-план.
