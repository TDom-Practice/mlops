# Automated Training Pipeline

## 1. High-level workflow automated training pipeline

### 1.1. Загальний опис

Automated Training Pipeline - це автоматизований процес запуску, виконання та контролю навчання ML-моделі. Його мета полягає в забезпеченні відтворюваності training runs, контролю якості даних і результатів навчання, прозорості виконання та керованого просування моделі до production.

Для реалізації процесу використовується інтеграція GitLab CI та AWS Step Functions.

GitLab CI відповідає за ініціацію workflow, перевірку умов запуску та передачу необхідного контексту до AWS. AWS Step Functions координує послідовність етапів навчання, контролює переходи між ними та обробляє помилки виконання.

Результати навчання, метрики й артефакти зберігаються в MLflow, а інформація про модель-кандидата реєструється в Model Registry.

### 1.2. High-level workflow

```text
GitLab Event / Manual Trigger
          |
          v
     GitLab CI Pipeline
          |
          | Передача commit SHA,
          | branch, model config
          v
 AWS Step Functions Execution
          |
          v
     Data Validation
          |
          v
      Training Job
          |
          v
    Model Evaluation
          |
          v
 Logging Metrics & Artifacts
          |
          v
 Quality Gates Validation
          |
          v
     Model Registry
          |
          v
  Notification to Team
          |
          v
     Manual Approval
          |
          v
 Staging / Production Release
```

Важливо розділяти технічний результат виконання pipeline та готовність моделі до production. Результати evaluation і артефакти зберігаються незалежно від проходження quality gates, щоб забезпечити аналіз кожного training run. Статус Candidate присвоюється лише моделі, яка пройшла автоматизовані quality gates. Перехід до production потребує окремого погодження та фактичного deployment.

### 1.3. Опис компонентів workflow

| Компонент | Призначення | Результат |
|---|---|---|
| GitLab Event / Manual Trigger | Ініціює запуск pipeline після визначеної події або вручну користувачем | Запит на запуск training |
| GitLab CI | Перевіряє умови запуску, передає параметри та ініціює AWS Step Functions | Запущений workflow |
| AWS Step Functions | Оркеструє послідовність етапів, контролює їх виконання, обробляє помилки та повторні спроби | Керований процес навчання |
| Data Validation | Перевіряє структуру, повноту, коректність та якість вхідних даних | Валідований dataset |
| Training Job | Виконує навчання моделі з визначеними параметрами та версіями даних | Навчена модель |
| Model Evaluation | Оцінює якість моделі та порівнює результати з baseline або production-моделлю | Результати оцінювання |
| Quality Gates | Перевіряє відповідність моделі встановленим критеріям якості | Рішення про проходження перевірок |
| MLflow | Фіксує параметри навчання, метрики, версії та артефакти | Збережений Training Run |
| Model Registry | Зберігає інформацію про модель, її версію, походження та статус lifecycle | Зареєстрована модель-кандидат |
| Notification | Інформує команду про результат виконання pipeline та наступні дії | Повідомлення про success або failure |

### 1.4. Розподіл відповідальності за ролями

- **Data Engineer:** відповідає за якість, структуру та готовність вхідних даних.
- **AI/ML Engineer:** відповідає за training code, навчання моделі, evaluation та інтерпретацію ML-метрик.
- **MLOps Engineer:** відповідає за стабільність pipeline, інтеграції, логування, Model Registry та моніторинг виконання.
- **Tech Lead:** оцінює технічну готовність рішення та погоджує технічні release-рішення.
- **AI PM:** координує процес, контролює виконання погоджених критеріїв, відстежує блокери й інформує стейкхолдерів.

Повідомлення про результат pipeline отримують відповідальні учасники команди. Owner відповідного етапу організовує аналіз помилки або результатів evaluation, а AI PM координує подальші дії.

### 1.5. Принципи контролю процесу

1. **Reproducibility:** кожен training run має містити версії коду й даних та параметри навчання.
2. **Traceability:** результати запуску доступні для перевірки й аудиту.
3. **Quality Control:** модель проходить автоматизовані quality gates до реєстрації зі статусом Candidate.
4. **Failure Handling:** помилки фіксуються, а відповідальний Owner отримує повідомлення.
5. **Cost Control:** запуски training jobs виконуються в межах погоджених ресурсних і бюджетних обмежень.
6. **Production Approval:** production release дозволяється лише після окремого погодження.

## 2. Контрольні точки pipeline

Для забезпечення стабільної роботи Automated Training Pipeline необхідно визначити контрольні точки (Control Points) на кожному ключовому етапі workflow.
Кожна контрольна точка повинна мати відповідального Owner-а, критерії успішного виконання та визначений порядок дій у разі виникнення помилки.
Це дозволяє своєчасно виявляти проблеми, уникати неконтрольованих переходів між етапами та забезпечувати прозорість процесу для всієї команди.

### 2.1. Таблиця контрольних точок

| Етап pipeline | Що перевіряє команда | Owner | Критерій успіху | Дії у разі помилки |
|---|---|---|---|---|
| Data Validation | Наявність вхідних даних, відповідність схеми, обов'язкові поля, пропущені значення, дублікати та коректність форматів | Data Engineer | Дані відповідають погодженій схемі та встановленим правилам якості | Зупинити pipeline, зафіксувати помилку, повідомити Data Engineer для перевірки та виправлення даних |
| Training Job | Коректність запуску training job, відповідність версії коду, даних і model config, доступність обчислювальних ресурсів | AI/ML Engineer | Training job завершився успішно, модель створена, результати збережені | Перевірити логи та причину помилки. За необхідності повторити запуск або створити incident |
| Model Evaluation | ML-метрики, відповідність threshold, порівняння з baseline або поточною production-моделлю | AI/ML Engineer | Модель відповідає встановленим порогам якості та не демонструє критичної деградації | Заблокувати реєстрацію Candidate, зафіксувати результати evaluation та передати їх AI/ML Engineer для аналізу |
| Logging | Наявність метрик, параметрів навчання, версій коду й даних та артефактів у MLflow | MLOps Engineer | Результати training run збережені незалежно від проходження quality gates | Перевірити інтеграцію з MLflow, доступи та збереження артефактів |
| Quality Gates | Відповідність ML-метрикам, бізнес-критеріям і baseline | AI/ML Engineer + AI PM / Business Owner | Усі обов'язкові автоматизовані перевірки пройдені | Заблокувати реєстрацію Candidate, зафіксувати причини та визначити подальші дії |
| Model Registry | Реєстрація моделі, яка пройшла quality gates, з версією, метаданими та посиланням на training run | MLOps Engineer | Модель зареєстрована зі статусом Candidate, її походження та результати можна перевірити | Перевірити помилки реєстрації, цілісність артефактів та інтеграцію з Registry |
| Manual Approval | Перевірка результатів evaluation та погодження моделі відповідальними особами | Tech Lead + AI PM / Business Owner | Отримано необхідне погодження для наступного release-етапу | Заблокувати release, зафіксувати причини та визначити подальші дії |
| Notification | Наявність повідомлення про результат pipeline, коректність статусу, метрик, посилань на логи та визначення наступного Owner-а | MLOps Engineer | Команда отримала повідомлення про success або failure з усією необхідною інформацією | Перевірити механізм сповіщень, повторити відправлення та повідомити відповідальних осіб альтернативним каналом |

### 2.2. Правила контролю виконання

Для всіх етапів pipeline діють такі правила:

1. **Sequential Execution:** залежний етап запускається лише після успішного завершення попереднього.
2. **Error Handling:** у разі помилки pipeline фіксує failed status, зберігає доступні логи та повідомляє відповідального Owner-а.
3. **Retry Policy:** повторні спроби дозволені для тимчасових технічних помилок. Проблеми з якістю даних або непроходження quality gates потребують усунення причини, а не автоматичного retry.
4. **Traceability:** кожен етап пов'язаний із training run, commit SHA, версією даних і параметрами моделі.
5. **Cost Control:** кількість повторних запусків та використання AWS-ресурсів обмежуються погодженими правилами.

### 2.3. Управлінський контроль

AI PM координує виконання погоджених критеріїв, відстежує блокери та інформує стейкхолдерів. Технічні Owner-и відповідають за результати своїх напрямів відповідно до розподілу ролей у розділі 1.4.
Перехід моделі до наступного етапу відбувається на основі перевірених результатів, а не лише факту успішного завершення попередньої операції.

## 3. Quality gates для нової моделі

Quality Gates - це набір контрольних перевірок, які визначають, чи відповідає нова ML-модель технічним і бізнес-вимогам перед її просуванням до наступного етапу lifecycle.
Успішне завершення Training Job означає лише те, що модель була технічно навчена. Для прийняття рішення щодо її подальшого використання необхідно окремо перевірити якість вхідних даних, результати оцінювання, стабільність метрик, відповідність бізнес-вимогам та наявність необхідних погоджень.

### 3.1. Перелік Quality Gates

| Quality Gate | Правило перевірки | Критерій успіху | Відповідальний | Рішення у разі невідповідності |
|---|---|---|---|---|
| Data Quality | Перевірка структури, повноти, типів даних, пропущених значень і дублікатів | Відсутні критичні помилки схеми, обов'язкові поля заповнені, дані відповідають погодженим правилам якості | Data Engineer | Зупинити pipeline до виправлення даних |
| Model Performance | Перевірка основних ML-метрик: F1-score, Precision, Recall | F1-score не нижче 0.80, Precision та Recall відповідають погодженим мінімальним значенням | AI/ML Engineer | Відхилити модель або повернути на додаткове навчання |
| Baseline Comparison | Порівняння результатів нової моделі з baseline або поточною production-моделлю | F1-score не нижче baseline, критичне погіршення інших метрик відсутнє | AI/ML Engineer | Не просувати модель, провести аналіз причин деградації |
| Business Performance | Перевірка впливу моделі на ключові бізнес-показники та важливі сегменти користувачів | Відсутнє критичне погіршення якості на ключових сегментах, бізнес-вимоги виконані | AI PM + Business Owner | Передати результати на додатковий аналіз, погодити подальші дії |
| Reproducibility | Перевірка можливості відтворити training run за збереженими версіями коду, даних і параметрами | Збережено commit SHA, версію dataset, model config та параметри навчання | MLOps Engineer | Заблокувати просування до усунення проблем із відтворюваністю |
| Logging & Artifacts | Перевірка наявності метрик, логів і model artifacts у MLflow | Усі обов'язкові результати доступні та пов'язані з відповідним training run | MLOps Engineer | Виправити логування та повторно зберегти результати |
| Approval | Окремий review результатів evaluation та погодження моделі | Отримано approval від Tech Lead та AI PM / Business Owner відповідно до release policy | Tech Lead + AI PM / Business Owner | Не дозволяти перехід до наступного release-етапу |
| Model Lifecycle | Перевірка відповідності статусу моделі результатам quality gates та approval | Модель отримала відповідний статус у Model Registry | MLOps Engineer | Заблокувати подальше просування до виправлення статусу |

### 3.2. Пороги ML-метрик

Для прикладу класифікаційної моделі пропонується використовувати такі початкові пороги:

| Метрика | Мінімальний поріг | Призначення |
|---|---|---|
| F1-score | ≥ 0.80 | Баланс між Precision та Recall |
| Precision | ≥ 0.80 | Контроль частки правильних позитивних прогнозів серед усіх позитивних прогнозів |
| Recall | ≥ 0.75 | Контроль здатності моделі знаходити позитивні випадки |

Окрім абсолютних значень метрик, результати нової моделі необхідно порівнювати з baseline або поточною production-моделлю на однаковому тестовому наборі даних. Наведені пороги є прикладом для класифікаційної моделі, а не універсальними значеннями: їх потрібно погодити з урахуванням baseline, бізнес-критичності помилок False Positive та False Negative і цільового сценарію використання.

Основне правило: нова модель повинна відповідати погодженим мінімальним порогам і не демонструвати неприйнятного погіршення якості порівняно з поточною моделлю.

### 3.3. Правила прийняття рішення

За результатами перевірок і погоджень модель проходить такі стани:

| Статус | Умова присвоєння | Подальші дії |
|---|---|---|
| Candidate | Training завершено, результати збережено, автоматизовані quality gates пройдено | Передати модель на review та manual approval |
| Approved | Модель пройшла необхідні перевірки й отримала погодження відповідальних осіб | Дозволити перехід до release-етапу |
| Rejected | Модель не відповідає обов'язковим критеріям якості або безпеки | Заборонити просування та зафіксувати причини відхилення |
| Production | Модель фактично розгорнута в production після всіх release-перевірок та approval | Моніторити модель відповідно до production policy |

Candidate та Approved описують стан перевірки й погодження моделі, тоді як Production означає фактичне розгортання. Конкретні назви та відображення статусів залежать від можливостей обраного Model Registry і deployment-процесу.

### 3.4. Manual Approval та відповідальність за рішення

Для переходу від Candidate до наступного release-етапу передбачається окреме manual approval. Production deployment також не може виконуватися без погодження, визначеного release policy.

Розподіл відповідальності:

- **AI/ML Engineer:** аналізує ML-метрики, результати evaluation та порівняння з baseline. Надає технічну рекомендацію щодо якості моделі.
- **MLOps Engineer:** перевіряє коректність реєстрації моделі, наявність артефактів, метаданих та результатів training run.
- **AI PM:** контролює виконання погоджених критеріїв, оцінює відповідність результатів бізнес-вимогам і координує процес погодження.
- **Tech Lead:** підтверджує технічну готовність моделі та погоджує її подальше просування.
- **Business Owner:** за необхідності підтверджує відповідність моделі бізнес-очікуванням.

Автоматичне проходження quality gates не замінює рішення відповідальних осіб щодо production release.

### 3.5. Дії у разі непроходження Quality Gates

Якщо модель технічно успішно навчилася, але не відповідає встановленим критеріям якості, застосовується такий порядок дій:

1. Pipeline фіксує результат evaluation та визначає, які саме quality gates не пройдено.
2. Модель не реєструється зі статусом Candidate; за потреби їй присвоюється статус Rejected із фіксацією причин.
3. AI/ML Engineer аналізує причини невідповідності: якість даних, параметри навчання, особливості моделі або деградацію метрик.
4. AI PM координує визначення подальших дій, відповідальних осіб та строків усунення проблеми.
5. Після виправлення причин запускається новий training run.
6. Нова версія моделі повторно проходить усі обов'язкові quality gates.

Таким чином, модель може вважатися технічно навченою, але залишатися непридатною для release. Остаточне рішення щодо production приймається лише після підтвердження якості, відповідності бізнес-вимогам та отримання необхідних погоджень.

## 4. Правила запуску training pipeline

Для ефективної роботи Automated Training Pipeline необхідно заздалегідь визначити умови, за яких запускається навчання моделі.
Вибір механізму запуску залежить від середовища розробки, частоти оновлення даних, результатів моніторингу моделі та потреб команди.
Основна мета полягає в тому, щоб забезпечити своєчасне оновлення моделей, зберігаючи контроль над обчислювальними ресурсами AWS та витратами на навчання.

### 4.1. Варіанти запуску pipeline

| Trigger | Коли доречний | Переваги | Ризики | Рекомендоване середовище |
|---|---|---|---|---|
| Push / Merge у dev branch | Після внесення змін у код моделі, training scripts або конфігурацію | Автоматизація перевірки змін, швидкий feedback для команди | Часті зміни можуть створювати зайві training runs та збільшувати витрати | Dev |
| Manual Trigger | Коли необхідно запустити навчання за рішенням відповідального спеціаліста | Контроль запусків, можливість перевірити готовність даних і ресурсів перед навчанням | Залежність від ручних дій, ризик затримки retraining | Staging / Production |
| Scheduled Trigger | Для регулярного оновлення моделі відповідно до погодженого графіка | Передбачуваність, регулярне оновлення моделі, планування ресурсів | Навчання може запускатися без реальної потреби, що створює додаткові витрати | Staging / Production |
| Model Config Change | Після зміни гіперпараметрів, feature configuration або інших параметрів моделі | Дозволяє перевірити вплив змін на якість моделі | Некоректні або часті зміни можуть спричинити зайві запуски | Dev / Staging |
| Drift Signal | Коли monitoring виявляє суттєву зміну розподілу вхідних даних або деградацію якості прогнозів | Дозволяє реагувати на зміни даних і погіршення якості моделі | Хибні сигнали drift можуть запускати непотрібне навчання; потрібен зрілий monitoring | Production |

### 4.2. Рекомендована стратегія запуску для різних середовищ

Для зменшення операційних ризиків пропонується використовувати різні правила запуску залежно від середовища.

**Development (Dev)**

Основний сценарій: автоматичний запуск після push або merge у dev branch, а також після зміни model config.

Особливості:
- Автоматична перевірка змін у training code.
- Запуск data validation перед навчанням.
- Можливість ручного запуску для експериментів.
- Використання обмежених обчислювальних ресурсів.
- Збереження результатів training runs для подальшого аналізу.

**Staging**

Основний сценарій: manual trigger або погоджений scheduled trigger.

Особливості:
- Перевірка готовності даних перед запуском.
- Використання конфігурації, наближеної до production.
- Повне оцінювання моделі та порівняння з baseline.
- Перевірка quality gates.
- Отримання approval перед переходом до наступного етапу.

**Production**

Основний сценарій: scheduled trigger або запуск після підтвердженого сигналу drift чи деградації якості.

Особливості:
- Запуск відповідно до погодженого графіка або результатів monitoring.
- Перевірка обґрунтованості retraining перед використанням ресурсів.
- Контроль бюджету та доступних обчислювальних ресурсів.
- Обов'язкове проходження всіх quality gates.
- Manual approval перед production release.

Важливо: автоматичний запуск retraining у production не повинен означати автоматичну заміну поточної production-моделі. Нова модель проходить повний цикл оцінювання та погодження окремо.

### 4.3. Правила контролю запусків

Для запобігання неконтрольованим запускам training pipeline пропонується встановити такі правила:

1. **Trigger Validation:** кожен запуск повинен відповідати погодженим умовам. Для push/merge необхідно враховувати, чи стосуються зміни training code, model config або інших компонентів ML-процесу.

2. **Duplicate Run Prevention:** система повинна перевіряти наявність активного execution для тієї самої моделі та конфігурації, щоб уникати дублювання запусків.

3. **Resource Limits:** для training jobs встановлюються обмеження на використання CPU/GPU, тривалість виконання та кількість повторних спроб.

4. **Budget Control:** для кожного середовища визначаються допустимі витрати на навчання. У разі перевищення погодженого бюджету нові запуски потребують додаткового погодження.

5. **Drift Confirmation:** сигнал drift повинен пройти перевірку встановлених порогів та тривалості відхилення, перш ніж ініціювати retraining.

6. **Failure Handling:** після невдалого запуску автоматичні повторні спроби дозволяються лише для визначених тимчасових помилок. Критичні помилки потребують аналізу відповідального Owner-а.

7. **Execution Tracking:** кожен запуск повинен мати унікальний execution ID та зберігати інформацію про trigger, commit SHA, branch і середовище виконання.

### 4.4. Рекомендована модель запуску

Для першої версії Automated Training Pipeline пропонується використовувати таку стратегію:

| Середовище | Основний trigger | Додатковий trigger | Контроль |
|---|---|---|---|
| Dev | Push / Merge у dev branch | Model Config Change, Manual Trigger | Автоматичні перевірки та обмеження ресурсів |
| Staging | Manual Trigger | Schedule | Повне оцінювання та перевірка quality gates |
| Production | Schedule | Drift Signal, Manual Trigger | Підтвердження необхідності retraining, контроль бюджету та обов'язковий approval перед release |

Такий підхід дозволяє поєднати автоматизацію розробки з контрольованим оновленням моделей у production.

У результаті часті експериментальні запуски залишаються в dev-середовищі, staging використовується для перевірки готовності моделі, а production retraining відбувається за визначеними правилами та під контролем відповідальних осіб.

## 5. Risk Assessment

Інтеграція GitLab CI з AWS Step Functions створює низку технічних та операційних ризиків, які необхідно оцінити до запуску Automated Training Pipeline у production.

Для управління ризиками використовується Risk Register, який містить оцінку ймовірності виникнення ризику, потенційного впливу на проєкт, заходи зменшення ризику та відповідального Owner-а.

Для оцінювання використовується три рівні:

- **Low:** низька ймовірність або незначний вплив на роботу системи.
- **Medium:** помірна ймовірність або вплив, який потребує контролю.
- **High:** висока ймовірність або критичний вплив на безпеку, стабільність чи результати роботи системи.

### 5.1. Risk Register

| ID | Ризик | Ймовірність | Вплив | Mitigation Strategy | Owner |
|---|---|---|---|---|---|
| R1 | Надмірні AWS-права для GitLab CI, які можуть дозволити доступ до ресурсів поза межами необхідного workflow | Medium | High | Використовувати принцип Least Privilege, окремі IAM Roles для dev/staging/prod та обмежувати доступ конкретними AWS-ресурсами й операціями | DevOps / MLOps Engineer |
| R2 | Компрометація облікових даних або AWS credentials, що використовуються під час CI/CD | Medium | High | Використовувати OIDC Federation для отримання тимчасових credentials замість постійних access keys. Обмежити термін дії сесій та перевіряти довірені GitLab claims | DevOps Engineer |
| R3 | Неконтрольоване зростання витрат на AWS через часті training runs, повторні запуски або використання дорогих GPU-ресурсів | High | High | Встановити бюджетні ліміти, AWS Budgets alerts, обмеження тривалості training jobs, кількості retry та використання обчислювальних ресурсів | MLOps Engineer + AI PM |
| R4 | Низька якість або некоректність вхідних даних призводить до отримання ненадійної моделі | Medium | High | Впровадити автоматизовану перевірку даних, контроль schema, data quality rules та версіонування datasets | Data Engineer |
| R5 | Нова модель демонструє гірші результати порівняно з поточною production-моделлю | Medium | High | Використовувати baseline comparison, погоджені ML thresholds та обов'язковий evaluation перед просуванням моделі | AI/ML Engineer |
| R6 | AWS Step Functions execution завершується помилкою через недоступність сервісів, timeout або некоректну передачу параметрів | Medium | Medium | Налаштувати error handling, timeout, контрольовані retry для тимчасових помилок, логування execution та процедуру відновлення | MLOps Engineer |
| R7 | Втрата або неповнота training artifacts, метрик і логів у MLflow | Medium | High | Забезпечити контроль збереження артефактів, резервування відповідних сховищ, перевірку доступності результатів та зв'язок із конкретним training run | MLOps Engineer |
| R8 | Неможливість відтворити результати навчання через відсутність версій даних, коду або параметрів моделі | Medium | High | Фіксувати commit SHA, dataset version, model config, залежності та параметри кожного training run | AI/ML Engineer + MLOps Engineer |
| R9 | Команда не отримує повідомлення про помилку pipeline, через що затримується реагування на проблему | Medium | Medium | Налаштувати автоматичні notifications для success/failure, контроль статусу доставки та альтернативний канал інформування для критичних помилок | MLOps Engineer |

### 5.2. Пріоритетні ризики та умови перед production

На основі Risk Register виділяються чотири групи ризиків, для яких до production необхідно підтвердити наявність конкретних заходів контролю.

**1. Security та контроль доступів (R1, R2)**

Основний пріоритет — захист AWS-інфраструктури та облікових даних.

До production-запуску необхідно:
- Налаштувати автентифікацію GitLab CI через OIDC.
- Перевірити IAM permissions та застосувати Least Privilege.
- Розділити доступи між середовищами.
- Переконатися, що постійні AWS credentials не зберігаються у відкритому вигляді в GitLab CI variables або репозиторії.

**2. Фінансовий контроль (R3)**

Необхідно забезпечити прогнозованість витрат на навчання моделей.

До production-запуску необхідно:
- Встановити бюджет для training jobs.
- Налаштувати AWS Budgets та сповіщення про перевищення витрат.
- Визначити максимальну тривалість виконання training job.
- Контролювати кількість повторних запусків та використання GPU-ресурсів.

**3. Надійність результатів навчання (R4, R5, R7, R8)**

Важливо забезпечити якість даних, достовірність результатів та можливість відтворення навчання.

До production-запуску необхідно:
- Перевірити автоматизацію data validation.
- Погодити baseline та мінімальні пороги ML-метрик.
- Забезпечити збереження training artifacts і метрик.
- Перевірити можливість відтворення training run за збереженими версіями коду та даних.

**4. Операційна надійність (R6, R9)**

Команда повинна мати можливість своєчасно виявляти та усувати проблеми.

До production-запуску необхідно:
- Перевірити обробку помилок і timeout у Step Functions.
- Визначити правила повторного запуску.
- Перевірити доставку success/failure notifications.
- Призначити відповідальних за реагування на критичні помилки.

### 5.3. Управління ризиками

AI PM координує процес управління ризиками: контролює наявність відповідальних Owner-ів, відстежує статус mitigation actions, організовує обговорення критичних проблем та інформує стейкхолдерів про ризики, які можуть вплинути на строки або production-readiness.

Технічні Owner-и відповідають за реалізацію заходів зменшення ризиків у межах своїх напрямів.

Перед production-запуском усі ризики з високим впливом повинні мати погоджені заходи контролю та відповідальних за їх реалізацію.

## 6. Acceptance Criteria для Jira-задачі

**Jira Task:** Інтегрувати GitLab CI з AWS Step Functions для automated training pipeline.

**Мета задачі:** Реалізувати керований запуск automated training workflow через GitLab CI з використанням AWS Step Functions, забезпечити передачу контексту запуску, контроль виконання етапів, збереження результатів, перевірку якості моделі та інформування команди.

### 6.1. Acceptance Criteria

- GitLab CI pipeline успішно запускає AWS Step Functions workflow.
- У Step Functions передаються Git-контекст запуску: commit SHA, branch, source та model configuration.
- Кожен запуск має унікальний execution ID, за яким можна знайти відповідний GitLab pipeline.
- Step Functions execution доступний для перегляду в AWS Console із можливістю відстеження статусу та окремих етапів виконання.
- Перед Training Job автоматично виконується Data Validation, яка перевіряє структуру та якість вхідних даних.
- У разі критичних помилок Data Validation training job не запускається.
- Training Job використовує визначені версії коду, даних і параметри моделі.
- Після завершення навчання автоматично запускається Model Evaluation із перевіркою ML-метрик та порівнянням із baseline.
- Параметри навчання, ML-метрики та model artifacts зберігаються в MLflow і доступні для перегляду.
- Перед реєстрацією моделі автоматично перевіряються погоджені Quality Gates та thresholds.
- Лише модель, яка пройшла Quality Gates, реєструється в Model Registry із відповідною версією, метаданими та статусом Candidate.
- Модель, яка не пройшла Quality Gates, не може бути автоматично просунута до наступного етапу lifecycle.
- Команда отримує notification про success або failure із зазначенням назви моделі, commit SHA, статусу виконання, ключових метрик та наступної дії.
- У разі помилки pipeline фіксує failed status, зберігає доступні логи та повідомляє відповідального Owner-а.
- Доступ GitLab CI до AWS налаштований через OIDC із використанням IAM Role та принципу Least Privilege.
- Постійні AWS credentials не використовуються для автентифікації GitLab CI.
- Автоматичний production release моделі заборонений без окремого manual approval від уповноваженої особи.
- Документовано послідовність workflow, параметри запуску, порядок перевірки результатів та дії у разі помилок.

### 6.2. Умови завершення Jira-задачі (Definition of Done)

Jira-задача вважається виконаною, якщо:

1. Усі Acceptance Criteria реалізовані та пройшли перевірку.
2. Проведено успішний тестовий запуск pipeline від GitLab CI до завершення AWS Step Functions workflow.
3. Перевірено сценарії успішного виконання та обробки помилок.
4. Підтверджено збереження метрик і артефактів у MLflow та реєстрацію моделі в Model Registry.
5. Перевірено отримання success/failure notifications.
6. Підтверджено коректність AWS permissions та відсутність надмірних доступів.
7. Перевірено блокування автоматичного production release без відповідного approval.
8. Технічна документація актуалізована та погоджена відповідальними учасниками команди.

**Важливо:** успішне виконання Jira-задачі підтверджує готовність інфраструктури automated training pipeline до використання. Воно саме по собі не означає, що конкретна ML-модель пройшла оцінювання та готова до production release.

## 7. Notification Messages

Після завершення Automated Training Pipeline команда отримує автоматичне повідомлення про результат виконання workflow.
Повідомлення повинні містити основну інформацію про запуск, його статус, результати та наступні дії.

### 7.1. Success Notification

```text
SUCCESS: Training pipeline completed

Model: churn_prediction_v3
Environment: Staging
Source: GitLab CI
Commit: a1b2c3d

Step Functions: execution-123
Metrics: F1-score = 0.84, Precision = 0.86, Recall = 0.82
Baseline F1-score: 0.81

Model Registry: Candidate

Details: MLflow Run / Model Registry / Step Functions

Next action: Review quality gates and approve the model for the next lifecycle stage.

Owner: AI/ML Engineer + Tech Lead
```

### 7.2. Failure Notification

```text
FAILED: Training pipeline execution

Model: churn_prediction_v3
Environment: Staging
Source: GitLab CI
Commit: a1b2c3d

Step Functions: execution-124
Failed step: Data Validation
Reason: Missing required column customer_age

Details: GitLab Job Logs / Step Functions / CloudWatch

Next action: Check dataset schema, fix the issue and restart the pipeline.

Owner: Data Engineer
```

### 7.3. Notification Requirements

Повідомлення повинні:
- Містити назву pipeline, модель, середовище та статус виконання.
- Вказувати commit SHA або branch і Step Functions execution ID.
- Відображати ключові ML-метрики та статус Model Registry у разі успішного виконання.
- Містити причину помилки й failed step у разі невдалого виконання.
- Надавати посилання на GitLab job, Step Functions execution, логи та результати training run.
- Визначати наступну дію та відповідального Owner-а.

Основний принцип: notification має бути коротким, зрозумілим і достатнім для того, щоб відповідальний учасник команди міг оперативно перейти до наступної дії.

## 8. Висновок

Automated Training Pipeline є важливою складовою MLOps, оскільки забезпечує автоматизацію, відтворюваність та контроль процесу навчання ML-моделей.  
GitLab CI відповідає за ініціацію workflow, перевірку умов запуску та передачу необхідного контексту до AWS.  
AWS Step Functions координує виконання етапів pipeline, забезпечує контроль їх послідовності та обробку помилок.  
MLflow і Model Registry забезпечують збереження результатів навчання, метрик, артефактів та інформації про версії моделей.  
Водночас успішне завершення training pipeline не гарантує готовності моделі до production, оскільки необхідно додатково підтвердити її якість, відповідність бізнес-вимогам та проходження quality gates.  
Рішення про production release має прийматися після перевірки результатів і отримання відповідних погоджень від відповідальних осіб.
